**녹음을 다루는 단위** = 맡긴 녹음의 내용을 읽는 서버 처리 단위 — 받기 단위(접수·길이 재기)와 처리 단위(전사). **녹음 읽기** = 맡긴 녹음 파일의
바이트를 해석하는 모든 일 — 길이 재기, 전사용 해독, 화자 구분용 음성 변환. **읽기 프로세스** = 녹음 읽기를 한 작업을 위해서만 하고 끝나면 사라지는
일회용 프로세스. **GPU 단계** = 해독된 음성으로 전사·화자 구분을 하는 단계. **해독된 음성** = 녹음 읽기가 내놓는 음성 자료(이 기능으로 새로 생기는
처리 중 음성). **직후** = 1분 안(001 과 같다). **시험용 대역** = 시험에서 읽기 프로세스 자리에 넣어 정해진 방식으로 실패하게 하는 가짜.

위협 모델: 이용자가 올린 녹음의 바이트는 믿지 않는다. 호출하는 쪽이 쓴 요청 문서는 001 의 경계 검사를 거친다. 운영자와 호출하는 쪽의 서비스 계정은 믿는다.
막으려는 것은 「해독기 취약점을 노린 녹음 하나가 읽기를 맡은 프로세스를 장악하는 경우」이고, 그때 그 프로세스가 닿을 수 있는 범위를 그 녹음 하나로 줄인다.

배포 단계(운영자 결정 2026-11-08): **P1** = User Story 1, 시범 기간(시험 계정만)에 먼저 배포. **P2** = User Story 2·3·4, bhu-llm 이 실제 이용자에게
열기(bhu-llm FR-659) 전에 배포. **P3** = User Story 5, 실제 이용자에게 열기 전.

### User Story 1 - 녹음을 다루는 단위가 쓸 수 있는 커널 기능을 좁힌다 (Priority: P1)

운영자는 녹음을 다루는 단위가 일반 서비스에 필요한 시스템 호출만 쓰게 제한한다. 그 범위를 넘는 허용은 꼭 필요한 것만, 이유와 함께 기록한다.
쓰기와 실행을 함께 허용하는 메모리는 막을 수 있는 단위에서 막는다. 정상 전사는 전과 똑같이 된다.

**Why this priority**: 인계가 「가장 효과가 크고 바로 할 수 있다」고 한 조치다. 해독기가 장악돼도 커널 취약점으로 격리 밖에 나갈 길이 좁아진다.
시범 기간에 단독으로 배포해 bhu-llm 의 남는 위험 하나를 바로 줄인다.

**Independent Test**: 이 이야기만 배포한 뒤 단위 설정을 조회하고, 정상 녹음의 1차·2차(화자 구분·힌트) 전사를 돌려 결과를 배포 전과 비교한다.

**Acceptance Scenarios**:

1. **Given** P1 이 배포됐다, **When** 운영자가 받기 단위와 처리 단위의 설정을 조회한다, **Then** 둘 다 시스템 호출 제한과 아키텍처 제한(그 기계의 기본 아키텍처 호출만 허용)이 켜져 있다 — 「제한 없음」이 아니다.
2. **Given** P1 이 배포됐다, **When** 운영자가 청소 단위와 모델 받기 단위의 설정을 조회한다, **Then** 같은 기본 제한이 켜져 있다.
3. **Given** 어떤 단위가 일반 서비스 범위 밖의 호출 묶음을 허용받았다, **When** 운영자가 저장소의 기록을 본다, **Then** 그 묶음마다 이유와 관측 근거가 있고, 기록에 없는 허용은 하나도 없다.
4. **Given** P1 이 배포됐다, **When** 운영자가 쓰기·실행 메모리 금지의 상태를 본다, **Then** 단위마다 「켬」 또는 「켤 수 없음」이 기록돼 있고, 「켤 수 없음」에는 거부된 지점을 잰 근거가 있다.
5. **Given** P1 이 배포됐다, **When** 기준 녹음 하나를 서버로 1차(힌트·화자 구분 없음)와 2차(힌트·화자 구분)로 전사한다, **Then** 둘 다 완료되고 전사록과 문단 목록이 배포 전과 같다(다르면 운영자가 차이를 확인하고 받아들인 뒤에만 완료로 친다).
6. **Given** P1 이 배포됐다, **When** 받기·청소·모델 받기가 평소 일(접수·거절·지우기 요청·매일 정리·고정 모델 확인)을 한다, **Then** 모두 배포 전과 같이 끝난다.

### User Story 2 - 녹음을 읽는 프로세스는 자기 작업의 녹음 밖에 닿지 못한다 (Priority: P2)

맡긴 녹음의 바이트는 작업마다 새로 뜨는 읽기 프로세스만 읽는다. 받기의 길이 재기, 전사용 해독, 화자 구분용 변환이 모두 그렇다. 읽기 프로세스는
자기 작업이 쓰는 녹음을 읽고 자기 출력을 쓸 수 있을 뿐, 다른 작업의 자료와 GPU 장치와 망에는 닿지 못한다. GPU 단계는 해독된 음성만 받는다.

**Why this priority**: 인계 요청 2·3. 해독기가 장악됐을 때 그날 다른 이용자의 녹음·전사록이 읽히거나 바뀌는 위험(인계 §3-1)과 GPU 드라이버로 가는 길(§3-3)을
없앤다. 실제 이용자에게 열기 전의 조건이다.

**Independent Test**: 서로 다른 요청자의 작업 둘이 서버에 있는 상태에서, 한 작업의 읽기 프로세스가 가진 권한으로 다른 작업의 자료와 GPU 장치에
접근해 보는 권한 점검을 하고, GPU 단계에 넘어가는 입력을 확인한다.

**Acceptance Scenarios**:

1. **Given** 요청자가 다른 작업 A·B 가 서버에 있다, **When** A 의 녹음 읽기가 돈다, **Then** 그 읽기 프로세스의 권한으로는 B 의 녹음·해독된 음성·힌트 사본·결과·요청·응답·상태 기록을 읽을 수도, 쓸 수도, 지울 수도 없다.
2. **Given** 1차 작업과 그 녹음을 가리키는 재전사 작업이 있다, **When** 재전사의 녹음 읽기가 돈다, **Then** 공유하는 녹음은 읽을 수 있고 1차의 결과·힌트 사본·해독된 음성은 읽을 수 없다.
3. **Given** 어떤 녹음 읽기가 돈다, **When** 그 읽기 프로세스의 권한으로 GPU 장치를 열려 한다, **Then** 거부된다.
4. **Given** 어떤 녹음 읽기가 돈다, **When** 그 읽기 프로세스의 권한으로 망에 접속하려 한다, **Then** 거부된다.
5. **Given** 녹음 읽기가 끝났다, **When** GPU 단계가 시작된다, **Then** GPU 단계가 받는 입력은 해독된 음성(과 작업 설정)뿐이고, 원래 녹음 파일의 위치나 내용은 넘어가지 않는다.
6. **Given** 서로 다른 두 작업, **When** 각 작업의 녹음 읽기가 돈다, **Then** 두 읽기는 서로 다른 읽기 프로세스이고, 한 읽기 프로세스가 두 작업의 녹음을 읽지 않는다.
7. **Given** 읽기 프로세스가 정상·실패·강제 종료로 끝났다, **When** 운영자가 서버를 본다, **Then** 그 읽기 프로세스는 남아 돌지 않고, 정해진 출력 밖에 남긴 파일이 없다.
8. **Given** 녹음이 붙은 요청을 맡긴다, **When** 받기가 길이를 재어 받아들이거나 거절한다, **Then** 접수 확인 또는 거절이 맡긴 직후 나온다(001 SC-011 과 같다).
9. **Given** 대기 없는 1시간 녹음, **When** 1차와 2차를 차례로 맡긴다, **Then** 처리 시간이 001 SC-001 안에 든다.

### User Story 3 - 녹음 읽기의 실패는 그 작업만 「읽을 수 없는 녹음」으로 끝난다 (Priority: P2)

녹음 읽기가 어떤 식으로 망가지든 — 오류를 내든, 판정 없이 끝나든, 정해진 메모리·시간 상한에 걸리든 — 그 작업만 `unreadable_audio`(읽을 수 없는 녹음)로
끝난다. 같은 줄의 다음 작업은 그대로 처리되고, 받기·처리·청소 단위는 멈추지 않는다.

**Why this priority**: 인계 §5 「조작 파일은 지금처럼 `unreadable_audio` 로 끝나고 다른 작업·단위는 영향을 받지 않아야 한다」. 지금은 해독기가 판정 없이
끝나면 `engine_error`, 메모리 상한에 걸리면 처리 단위 전체가 멈출 수 있다(tech-notes §5). 이용자는 분명한 이유를, 운영자는 흔들리지 않는 단위를 얻는다.

**Independent Test**: 읽기 프로세스 자리에 시험용 대역을 넣어 실패 방식마다 작업을 하나씩 맡기고, 바로 뒤에 정상 작업을 맡긴다.

**Acceptance Scenarios**:

1. **Given** 텍스트 파일에 녹음 확장자를 붙인 첨부(인계 §6), **When** 호출하는 쪽이 맡긴다, **Then** 받기가 `unreadable_audio` 로 거절하고, 받기 단위는 정상으로 끝나며, 함께 맡긴 다른 요청은 그대로 처리된다.
2. **Given** 받기의 길이 재기 읽기 프로세스가 판정 없이 끝나거나 상한에 걸린다(시험용 대역), **When** 받기가 그 요청을 처리한다, **Then** 그 요청은 `unreadable_audio` 로 거절되고, 같은 묶음의 다른 요청은 그대로 처리된다.
3. **Given** 처리 단계의 녹음 읽기가 오류를 낸다(시험용 대역), **When** 작업이 끝난다, **Then** 그 작업은 `unreadable_audio` 로 실패하고 결과는 없다.
4. **Given** 처리 단계의 녹음 읽기가 판정 없이 끝난다(시험용 대역), **When** 작업이 끝난다, **Then** 그 작업은 `unreadable_audio` 로 실패한다 — `engine_error` 가 아니다.
5. **Given** 처리 단계의 녹음 읽기가 자기 메모리 상한 또는 시간 상한에 걸린다(시험용 대역), **When** 작업이 끝난다, **Then** 그 작업은 `unreadable_audio` 로 실패하고, 처리 단위는 멈추지 않는다.
6. **Given** 위 3~5 의 실패 작업 바로 뒤에 정상 작업이 기다린다, **When** 실패 작업이 끝난다, **Then** 정상 작업이 완료된다.
7. **Given** 녹음 읽기는 끝났고 GPU 단계에서 오류가 난다(GPU 메모리 부족 등), **When** 작업이 끝난다, **Then** 실패 이유는 지금의 분류(`gpu_out_of_memory`·`engine_error` 등) 그대로다.
8. **Given** 서버가 읽기 프로세스를 띄우지조차 못했다(녹음과 무관한 서버 문제), **When** 처리 단계의 작업이 끝난다, **Then** `unreadable_audio` 가 아니라 `engine_error` 로 실패한다.
9. **Given** 어떤 실패든, **When** 응답이 나온다, **Then** 실패 설명은 정해진 고정 문장이고 해독기의 오류 원문은 없다.

### User Story 4 - 계약과 삭제 약속은 그대로다 (Priority: P2)

격리가 강화돼도 bhu-llm 이 보는 것은 하나도 바뀌지 않는다. 격리 때문에 새로 생기는 자료(해독된 음성 등)도 다른 처리 중 음성과 똑같이 지워진다.

**Why this priority**: bhu-llm 029 는 stt 계약 `ce5c325` 에 맞춰져 있다(인계 §5). 새 중간 자료가 삭제에서 빠지면 「반드시 삭제」가 거짓이 된다(헌법 III).
P2 와 같이 배포되므로 같은 우선순위다.

**Independent Test**: 형식 정의 파일을 배포 전과 비교하고, 한 녹음에 작업 5개를 차례로 맡긴 뒤, 「다 지우기」·매일 정리·강제 종료 경우마다 남은 파일을 센다.

**Acceptance Scenarios**:

1. **Given** P2 가 배포됐다, **When** 호출하는 쪽에 내놓은 요청·응답·결과 형식 정의와 판 번호를 배포 전과 비교한다, **Then** 같다.
2. **Given** 한 녹음, **When** 1차·자동 2차·재전사 3번을 차례로 맡긴다(작업 5개), **Then** 다섯 작업이 모두 완료된다.
3. **Given** 한 녹음을 쓴 작업들의 결과와 해독된 음성이 있다, **When** 「다 지우기」를 보낸다, **Then** 그 녹음과 그 녹음을 쓴 모든 작업의 파일이 직후 0개다.
4. **Given** 녹음 읽기가 도는 중이다, **When** 그 녹음의 「다 지우기」가 온다, **Then** 읽기 프로세스가 멈추고 그 작업의 파일이 직후 0개다.
5. **Given** 그날 받은 작업들의 해독된 음성이 남아 있거나 녹음 읽기가 도는 중이다, **When** 23:58 매일 정리가 돈다, **Then** 해독된 음성과 읽기 프로세스의 출력이 모두 0개다.
6. **Given** 처리 단위가 녹음 읽기 중에 강제로 멈췄다, **When** 다음 처리 시작이나 청소가 돈다, **Then** 그 작업은 지금처럼 `interrupted` 가 되고 해독된 음성과 출력이 0개다.
7. **Given** P2 가 배포됐다, **When** 운영자가 명령줄로 전사·화자 구분·일괄 처리를 한다, **Then** 동작과 출력이 배포 전과 같다.

### User Story 5 - 녹음을 여는 구성 요소의 판과 갱신 정책을 기록한다 (Priority: P3)

운영자는 녹음을 여는 구성 요소마다 지금 판, 그 판을 고정한 곳, 그 판이 들어온 날, 마지막 갱신일을 저장소 문서에서 보고, 정해 둔 정책에 따라 올린다.

**Why this priority**: 인계 요청 4. 지금은 정책도 기록도 없고 판이 2026-07-31·08-02 에 고정된 뒤 그대로다. 문서 일이라 격리보다 뒤지만 실제 이용자에게 열기 전에 갖춘다.

**Independent Test**: 문서 하나를 열어 구성 요소 목록이 녹음 읽기에 쓰이는 것을 빠짐없이 덮는지, 날짜가 저장소 기록과 맞는지 본다.

**Acceptance Scenarios**:

1. **Given** 저장소 문서, **When** 운영자가 녹음을 여는 구성 요소 목록을 본다, **Then** 녹음 읽기에 쓰이는 모든 구성 요소가 있고 각각 지금 판·고정한 곳·들어온 날·마지막 갱신일이 있다.
2. **Given** 저장소 문서, **When** 운영자가 갱신 정책을 본다, **Then** 누가(운영자), 얼마 주기로(매달), 무엇을 보고(보안 공지·새 판 소식·배포판 갱신) 올리는지와 보안 공지 뒤 7일 기한이 있다.
3. **Given** 구성 요소 하나를 올리는 배포, **When** 배포를 마친다, **Then** 기록의 판과 날짜가 바뀌어 있고 기준 녹음 비교(US1-5 와 같은 방법)를 거쳤다.
4. **Given** 한 달이 지났다, **When** 운영자가 기록을 본다, **Then** 그달의 확인 날짜가 있다 — 새 판이 없어 올리지 않은 달도 확인한 날은 남는다.
5. **Given** 녹음 읽기에 쓰이는 구성 요소의 보안 공지가 나왔다, **When** 7일이 지난다, **Then** 그 구성 요소가 올라가 있거나 올리지 않은 이유가 기록돼 있다.

---

### Edge Cases

1. 2차가 아직 끝나지 않은 1차의 녹음을 가리킨다(001 의 대기 중 1차 가리키기): 두 작업의 녹음 읽기는 각자의 읽기 프로세스에서 돌고, 서로의 출력을 보지 못한다.
2. 받기의 길이 재기와 처리 단계의 해독이 같은 때 다른 작업에 대해 돈다: 두 읽기 프로세스는 서로 닿지 못한다.
3. 3시간 한도에 딱 맞는 정상 녹음: 읽기 프로세스의 메모리·시간 상한이 이 녹음을 실패시키지 않는다.
4. 작업 전체의 처리 시간 상한이 녹음 읽기 중에 먼저 온다: `processing_timeout` 으로 끝난다(지금과 같다). 읽기 프로세스 자신의 상한이 먼저 오면 `unreadable_audio`.
5. 해독된 음성을 쓰던 중 저장 공간이 찬다: 읽기 프로세스가 띄워진 뒤의 실패이므로 `unreadable_audio`, 남은 파일 0.
6. 같은 녹음을 다시 전사할 때: 녹음 읽기를 다시 할지 앞 작업의 해독된 음성을 다시 쓸지는 plan 이 정한다. 어느 쪽이든 공유하는 것은 그 녹음에서 나온 자료뿐이고 삭제 규칙(US4)을 따른다.
7. 시스템 호출 제한이 드문 경로에서만 필요한 호출을 막는다(예: 화자 구분, 목소리 비교, 모델 확인): 호스트 시험이 1차·2차·화자 구분·모델 받기를 모두 한 번씩 거친다(US1-5·6).
8. 운영자가 명령줄로 같은 서버에서 전사한다: 명령줄은 격리 대상이 아니고, GPU 줄 서기는 그대로다.
9. 녹음 확장자는 맞지만 형식 허용목록 밖의 형식인 녹음: 지금처럼 받기에서 `unreadable_audio`(001 FR-004a).

## Requirements *(mandatory)*

### Functional Requirements

**P1 — 커널 기능 좁히기**

- **FR-001**: 녹음을 다루는 단위(받기·처리)는 일반 서비스에 필요한 범위의 시스템 호출만 쓸 수 있고, 그 기계의 기본 아키텍처 밖의 호출 경로는 막혀 있어야 한다(MUST, 인계 §4-1).
- **FR-002**: 일반 서비스 범위를 넘는 허용은 단위마다 꼭 필요한 묶음만 둔다. 묶음마다 이유와 관측 근거를 저장소에 기록하고, 기록에 없는 허용을 두지 않는다(MUST).
- **FR-003**: 쓰기와 실행을 함께 허용하는 메모리는 막을 수 있는 단위에서 막는다. 막지 못하는 단위는 거부된 지점을 잰 근거를 기록한다(MUST, 인계 §4-1).
- **FR-004**: 청소 단위와 모델 받기 단위에도 같은 기본 제한을 건다(MUST — Assumptions 참고). 모델 받기 단위의 망 허용은 지금 그대로다.
- **FR-005**: 제한은 정상 동작을 바꾸지 않는다 — 1차·2차·화자 구분·힌트 전사, 받기·청소·모델 받기의 평소 일이 배포 전과 같이 끝난다(MUST).

**P2 — 녹음 읽기 격리**

- **FR-006**: 맡긴 녹음의 바이트를 해석하는 모든 일(길이 재기, 전사용 해독, 화자 구분용 변환)은 그 작업만을 위해 새로 뜨는 읽기 프로세스에서만 한다. 한 읽기 프로세스가 두 작업의 녹음을 읽지 않는다(MUST, 인계 §4-2, 운영자 결정 2026-11-08: 길이 재기 포함).
- **FR-007**: 읽기 프로세스는 자기 작업이 쓰는 녹음을 읽고 자기 출력을 쓸 수만 있다. 다른 작업의 녹음·해독된 음성·힌트 사본·결과·요청·응답·상태 기록은 읽기·쓰기·지우기가 모두 거부된다. 같은 녹음을 쓰는 작업끼리도 그 녹음 밖의 자료는 거부된다(MUST, 인계 §4-3).
- **FR-008**: 읽기 프로세스는 GPU 장치를 열 수 없고, 망에 닿을 수 없으며, FR-001 의 제한(또는 더 좁은 제한)을 받는다(MUST).
- **FR-009**: 읽기 프로세스에는 그 프로세스만의 메모리·시간 상한이 있다. 상한에 걸리면 그 프로세스만 끝나고 받기·처리·청소 단위는 멈추지 않는다. 상한은 3시간 한도 안의 정상 녹음을 실패시키지 않는다(MUST).
- **FR-010**: GPU 단계는 해독된 음성과 작업 설정만 입력으로 받는다. 원래 녹음 파일의 위치나 내용은 GPU 단계에 넘어가지 않고, GPU 단계는 녹음을 해독하지 않는다(MUST, 인계 §4-2).
- **FR-011**: 읽기 프로세스가 정상·실패·강제 종료로 끝나면 그 프로세스는 남아 돌지 않고, 정해진 출력 밖의 파일을 남기지 않는다(MUST).
- **FR-012**: 해독된 음성 등 이 기능으로 새로 생기는 자료는 001 의 처리 중 음성과 같은 삭제 규칙을 따른다 — 「다 지우기」 직후, 매일 23:58 정리, 처음 받은 때로부터 24시간 안, 스왑·오류 덤프에 남기지 않음, 암호화된 저장 위치에만, 백업 제외. 정상·실패·강제 종료 모두(MUST, 헌법 III, 001 FR-035).
- **FR-013**: 「다 지우기」나 매일 정리가 녹음 읽기 중에 오면 읽기 프로세스를 멈추고 그 출력을 지운다. 걸리는 시간은 001 의 처리 중 지우기와 같다(직후, 001 SC-005)(MUST).
- **FR-014**: 받기의 접수 확인·거절은 맡긴 직후 나오고(001 SC-011), 1시간 녹음의 처리 시간은 001 SC-001 안에 든다(MUST).

**실패 이유**

- **FR-015**: 읽기 프로세스가 띄워진 뒤의 모든 실패 — 오류, 판정 없이 끝남, 자기 메모리·시간 상한 초과 — 는 `unreadable_audio` 로 끝난다. 받기에서는 그 요청의 거절, 처리 단계에서는 그 작업의 실패다(MUST, 운영자 결정 2026-11-08, 인계 §5).
- **FR-016**: 서버가 읽기 프로세스를 띄우지 못한 경우는 녹음 탓이 아니므로 `unreadable_audio` 로 알리지 않는다 — 처리 단계에서는 `engine_error`, 받기에서는 001 FR-032a 의 요청별 오류 처리를 따른다(MUST).
- **FR-017**: 한 작업의 녹음 읽기 실패는 같은 줄의 다른 작업과 같은 받기 묶음의 다른 요청에 영향을 주지 않는다(MUST, 인계 §5).
- **FR-018**: GPU 단계의 실패 분류(`gpu_out_of_memory`·`gpu_unavailable`·`models_unavailable`·`engine_error`)와 작업 전체 처리 시간 상한의 `processing_timeout` 은 그대로다. 작업 전체 상한과 읽기 프로세스 상한 가운데 먼저 온 것이 이유를 정한다(MUST).
- **FR-019**: 실패 설명은 정해진 고정 문장이고, 해독기의 오류 원문·경로·녹음 내용을 싣지 않는다(MUST, 001 과 같다). 로그는 001 FR-037 의 범위(작업 ID·상태·이유·시각)를 넘지 않는다.

**계약과 기존 동작**

- **FR-020**: 요청·응답·결과 형식 정의와 판 번호, inbox·outbox 의 경로와 권한, 「다 지우기」의 의미(그 녹음을 쓴 모든 요청), 앞 작업 녹음으로 다시 전사하기, 23:58 정리는 그대로다. 바꿔야 한다면 먼저 인계 문서로 알리고 운영자 승인 뒤에 바꾼다(MUST, 헌법 VI, 인계 §5).
- **FR-021**: 실패 이유를 새로 만들지 않는다 — 응답의 실패 이유 목록은 그대로다(MUST).
- **FR-022**: 운영자의 명령줄 전사·화자 구분·일괄 처리의 동작과 출력은 그대로다. 명령줄은 격리 대상이 아니다(MUST, 001 FR-040).
- **FR-023**: 운영자는 단위의 비정상 종료와 작업 하나의 정상적인 실패를 구별해 볼 수 있어야 한다(MUST, 인계 §5). stt 는 알림을 보내는 길을 새로 만들지 않는다 —
  작업 실패는 응답의 실패 이유로, 단위의 비정상 종료는 서버의 단위 상태와 로그로 구별하고, 그 확인 방법을 운영 문서와 회신(FR-027)에 적는다
  (운영자 결정 2026-11-08). 서버 전체 단위의 실패 알림은 호스트 설정(nixos-config)의 별도 과제다.

**P3 — 갱신 정책**

- **FR-024**: 저장소 문서 하나에 녹음 읽기에 쓰이는 모든 구성 요소의 지금 판, 고정한 곳, 그 판이 들어온 날, 마지막 갱신일이 있다(MUST, 인계 §4-4).
- **FR-025**: 같은 문서에 갱신 정책이 있고 그대로 지킨다(MUST, 운영자 결정 2026-11-08): 운영자가 매달 한 번 녹음 읽기에 쓰이는 구성 요소의 새 판이
  있는지 확인하고 새 판이 있을 때만 올린다. 확인하는 곳은 해독기의 보안 공지, 해독기의 새 판 소식, 서버 배포판의 해독기 갱신이다. 해독기 보안 공지가
  나오면 7일 안에 올리거나, 올리지 않는 이유(이 서버의 판에 해당하지 않음 등)를 기록한다. 매달 확인한 날도 기록한다.
- **FR-026**: 구성 요소를 올리는 배포는 기록을 고치고 기준 녹음 비교(US1-5 와 같은 방법)를 거친다(MUST).

**회신과 확인 방식**

- **FR-027**: P1 배포 뒤와 P2 배포 뒤에 각각 회신 인계 문서를 낸다 — 인계 §6 의 확인 결과(설정 조회 값, 시험 결과), 요청 1~4 와 §5 질문의 답, bhu-llm 측정 문서의 보관 기간 질문의 답. 운영자를 거쳐 bhu-llm 대장 A18 에 적힌다(MUST, 인계 §7, 헌법 VI). 지금 판과 날짜(FR-024)는 P1 회신에 먼저 싣는다.
- **FR-028**: 격리는 설정 조회와 권한 점검으로, 실패 처리는 시험용 대역으로, 조작 파일은 인계 §6 의 시험 파일(녹음 확장자를 붙인 텍스트 파일)로 확인한다. 해독기 취약점을 실제로 노리는 파일은 만들거나 보관하지 않는다(MUST NOT).

### Key Entities

- **읽기 프로세스**: 한 작업의 녹음 읽기 한 번을 맡는 일회용 실행 단위. 어느 작업을 위한 것인지, 읽을 수 있는 녹음 하나, 쓸 수 있는 출력 자리, 메모리·시간 상한, 끝난 방식(정상·실패·판정 없음·상한 초과)을 가진다. 작업이 끝나면 남지 않는다.
- **해독된 음성**: 녹음 읽기가 내놓는 음성 자료. 하나의 녹음에서 나오고 그 녹음을 쓰는 작업에 딸린다. 001 의 처리 중 음성과 같은 삭제 규칙을 따른다. 상태 기록이나 결과에 드러나지 않는다.
- **제한 예외 기록**: 단위마다 일반 서비스 범위를 넘어 허용한 호출 묶음, 그 이유와 관측 근거, 쓰기·실행 메모리 금지의 상태(켬/켤 수 없음과 근거).
- **구성 요소 판 기록**: 녹음 읽기에 쓰이는 구성 요소마다 지금 판, 고정한 곳, 들어온 날, 마지막 갱신일. 갱신 정책을 함께 담는다.
- **회신 인계 문서**: 단계(P1·P2)마다 bhu-llm 으로 가는 답. 확인 결과와 요청·질문별 답을 담는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 설정 조회에서 stt 의 서버 단위 4개 모두 시스템 호출 제한과 아키텍처 제한이 켜져 있고(지금 0개), 기록에 없는 예외 허용이 0개다. 쓰기·실행 메모리 금지는 4개 단위 모두 상태와 근거가 기록돼 있다.
- **SC-002**: 권한 점검에서 읽기 프로세스의 권한으로 다른 작업의 자료(녹음·해독된 음성·힌트 사본·결과·요청·응답·상태 기록)를 읽기·쓰기·지우기 한 시도의 성공이 0건이고, GPU 장치 열기·망 접속 시도의 성공도 0건이다.
- **SC-003**: GPU 단계에 넘어간 입력에서 원래 녹음 파일이 나온 경우가 모든 시험 작업에서 0건이다.
- **SC-004**: 녹음 확장자를 붙인 텍스트 파일은 100% `unreadable_audio` 로 끝나고, 같은 때 맡긴 정상 녹음은 100% 완료된다.
- **SC-005**: 시험용 대역의 실패 방식 4가지(오류, 판정 없이 끝남, 메모리 상한, 시간 상한) 각각에서 그 작업은 `unreadable_audio` 로 끝나고, 바로 뒤 정상 작업은 완료되며, 받기·처리·청소 단위의 비정상 종료는 0건이다.
- **SC-006**: 호출하는 쪽에 내놓은 형식 정의 파일의 변경이 0바이트이고, 한 녹음을 쓴 작업 5개가 모두 완료되며, 「다 지우기」 직후 그 녹음을 쓴 작업들의 파일이 0개다.
- **SC-007**: 기존 시험이 모두 통과하고, 기준 녹음의 1차·2차 전사록과 문단 목록이 배포 전과 같으며(다르면 운영자가 받아들인 뒤에만 완료), 1시간 녹음의 처리 시간이 001 SC-001 안에, 접수 확인이 001 SC-011 안에 든다.
- **SC-008**: 새로 생기는 자료의 남은 파일이 정상·실패·강제 종료·「다 지우기」·23:58 정리의 다섯 경우 모두에서 0개다.
- **SC-009**: 녹음 읽기에 쓰이는 구성 요소의 100% 가 판·고정한 곳·들어온 날·마지막 갱신일과 함께 문서에 있고, 갱신 정책이 같은 문서에 있다.
  배포 뒤 매달 확인 날짜가 빠진 달이 0개이고, 보안 공지 뒤 7일 안에 갱신 또는 이유 기록이 없는 공지가 0건이다.
- **SC-010**: P1·P2 배포 뒤 각각 회신 인계 문서가 운영자에게 넘어간다(모두 2건). 각 문서는 인계 요청 1~4 와 §5 질문에 하나도 빠짐없이 답한다.

## Assumptions

- 대상은 서버 경로뿐이다. 명령줄은 운영자 자신의 파일을 운영자의 기기에서 다루므로 격리하지 않는다(인계 범위가 서버 단위다).
- 청소·모델 받기 단위에도 P1 의 기본 제한을 건다(FR-004). 인계는 녹음을 다루는 두 단위만 요청했지만, 청소도 모든 작업의 자료에 닿고, 모든 단위가 같은
  기본 제한을 나누면 따로 두는 것보다 단순하다. idea 의 미결 질문 셋째를 이렇게 정했다 — `/speckit-clarify` 에서 바꿀 수 있다.
- 읽기 프로세스가 띄워진 뒤의 실패는 원인을 가리지 않고 `unreadable_audio` 다(저장 공간 부족 포함 — 경계 사례 5). 띄우기 전의 실패만 서버 문제로 본다(FR-016).
- 해독된 음성을 녹음마다 한 번 만들어 재사용할지, 작업마다 새로 만들지는 plan 이 정한다. 3시간 녹음의 해독된 음성은 수백 MB 이고 암호화된 저장 위치에 그만한 여유가 있다고 본다(tech-notes §4, plan 에서 확인).
- 업로드 직후 파일 머리로 형식을 확인하는 보조책은 bhu-llm 의 일이고 이 기능에 들지 않는다(인계 §7).
- 이 서버(GPU 한 장, 램 32GB)에서 돈다. VM 시험은 GPU 가 없어 GPU 쪽 확인(시스템 호출 예외, GPU 장치 거부, 1·2차 전사)은 호스트 시험에서 한다.
- 시범 기간에는 시험 계정만 쓴다. P1 만 배포된 동안 남는 위험(같은 계정·같은 저장 위치, GPU 단위의 해독)은 bhu-llm 대장 A18 에 남고 운영자가 받아들일지 정한다.
- 확인 방식(FR-028)은 001 최종 감사(T078)의 교훈을 따른다 — 공격 입력을 만들던 첫 실행은 보고 없이 끝났다. project-audit 의 adversary 도 읽기만 한다.
