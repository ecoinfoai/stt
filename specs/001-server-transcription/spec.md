## User Scenarios & Testing *(mandatory)*

용어: **호출하는 쪽** = bhu-llm(이용자 대신 작업을 맡기는 시스템). **이용자** = bhu-llm 을 쓰는 교수·직원. **운영자** = stt 를
명령줄로 직접 쓰는 사람. **힌트 단어장** = 전사할 때 쓰도록 작업에 딸려 오는 용어 목록(전사 단어장 (2)). 참조 단어장 (1)은 stt 에 오지 않는다.
**직후** = 정한 일·시각에서 1분 안. **매일 정리** = 매일 23:58(KST)에 그 시각 전에 받은 모든 작업의 자료(녹음·처리 중 음성·힌트 단어장
사본·결과·상태)를 지우는 일. **다 지우기** = 호출하는 쪽이 이용자가 일을 마쳤다고 알리며 보내는 지우기 요청(유일한 지우기 요청).

### User Story 1 - 녹음을 맡기고 전사록을 받는다 (Priority: P1)

호출하는 쪽이 이용자의 녹음 하나를 맡긴다. stt 는 접수를 확인하고 차례가 오면 전사해, 전사록·문단 목록·실행 요약을 정해진 형식으로 돌려준다.
화자 구분을 고르면 `화자1`·`화자2` 로만 표시한다. 힌트 단어장을 붙이면 몇 개가 반영됐는지 알린다.

**Why this priority**: 이것 없이는 bhu-llm 이 stt 를 부를 수 없다. 나머지 이야기는 모두 이 위에 선다.

**Independent Test**: 시험 녹음 하나를 화자 구분·힌트 단어장 조합별로 맡기고, 돌아온 결과를 stt 가 내놓은 형식 정의로 검사한다.

**Acceptance Scenarios**:

1. **Given** 대기 중인 작업이 없다, **When** 호출하는 쪽이 녹음 하나를 맡긴다, **Then** 접수 확인과 대기 순서가 바로 나오고, 완료되면 상태가 「완료」로 바뀌며 전사록·문단 목록·실행 요약이 나온다.
2. **Given** 화자 구분을 고른 작업, **When** 전사가 끝난다, **Then** 모든 문단에 `화자N` 형식의 화자와 시작·끝 시각이 있고, 화자 판정이 불확실한 짧은 문단에는 불확실 표시가 있으며, `화자N` 밖의 이름은 없다.
3. **Given** 화자 구분을 고르지 않은 작업, **When** 전사가 끝난다, **Then** 문단에 화자가 없고 시작·끝 시각은 있다.
4. **Given** 엔진 한도 안에 드는 힌트 단어장, **When** 전사가 끝난다, **Then** 실행 요약에 「반영 M개 / 전체 M개」가 있고 빠진 용어는 없다.
5. **Given** 엔진 한도를 넘는 힌트 단어장, **When** 전사가 끝난다, **Then** 전사는 완료되고, 실행 요약에 「반영 N개 / 전체 M개」(N < M)와 빠진 용어 전부가 단어장 순서대로 있다.
6. **Given** 힌트 단어장이 없는 작업, **When** 전사가 끝난다, **Then** 실행 요약에 단어장 항목이 없다.
7. **Given** 이미 두 작업이 기다리고 있다, **When** 새 작업을 맡긴다, **Then** 대기 순서 3이 나오고, 앞 작업이 끝날 때마다 순서가 줄어든다.
8. **Given** 어떤 작업이든, **When** 호출하는 쪽이 받은 결과를 형식 정의로 검사한다, **Then** 통과한다.

### User Story 2 - 원본과 결과는 반드시 지워진다 (Priority: P1)

녹음은 개인정보다. 이용자가 일을 마치면(1차에서 멈추든 2차까지 하든) 호출하는 쪽이 「다 지우기」를 요청하고, stt 는 그 녹음과 그
녹음을 쓴 작업들의 처리 중 음성·단어장 사본·결과를 즉시 모두 지운다. 요청이 없어도 매일 정리(23:58 KST)가 그 시각 전에 받은 모든
작업의 자료와 상태를 지운다. 그래서 어떤 자료도 처음 받은 때로부터 24시간을 넘지 않는다. 매일 정리 때 대기·처리 중인 작업도 멈추고
함께 지운다 — 늦은 시각에 맡긴 작업이 끝나지 못할 수 있음은 호출하는 쪽이 이용자에게 미리 알린다.

**Why this priority**: 운영자 결정 「음원 자체가 개인정보 — 전사 뒤 반드시 삭제」가 서비스 개시의 조건이다. 삭제가 한 곳이라도 빠지면 약속이 거짓이 된다.

**Independent Test**: 지우는 길(「다 지우기」·매일 정리)과 종료 방식(정상·실패·강제 종료)의 조합으로 시험 작업을 돌리고, 지운 직후 서버의 모든 저장 위치를 확인한다.

**Acceptance Scenarios**:

1. **Given** 완료된 작업, **When** 「다 지우기」를 요청한다, **Then** 직후 녹음·처리 중 음성·단어장 사본·결과가 서버 어디에도 없고, 지운 사실이 상태에 남는다.
2. **Given** 1차와 2차가 같은 녹음을 쓴다, **When** 둘 중 하나를 대상으로 「다 지우기」를 요청한다, **Then** 직후 녹음과 두 작업의 단어장 사본·결과가 모두 없고, 두 작업 모두 「지움」이다.
3. **Given** 처리 중인 작업, **When** 「다 지우기」를 요청한다, **Then** 처리를 멈추고 모든 파일을 지우며, 일부 결과도 남기지 않는다.
4. **Given** 대기 중인 작업, **When** 「다 지우기」를 요청한다, **Then** 처리하지 않고 녹음·단어장 사본을 지우며 「지움」이 된다.
5. **Given** 지우기 요청이 없던 작업들(완료·실패·대기·처리 중), **When** 23:58 KST 가 된다, **Then** 직후 그 작업들의 녹음·처리 중 음성·단어장 사본·결과·상태가 서버 어디에도 없고, 처리 중이던 작업은 멈춘다.
6. **Given** 23:58 이후에 받은 작업, **When** 그날의 매일 정리가 돈다, **Then** 그 작업은 지워지지 않고 다음 날 23:58 정리 때 지워진다.
7. **Given** 처리 중인 작업, **When** 처리가 강제로 끊긴다(전원·프로세스 종료), **Then** 작업은 「실패 — 중단」으로 끝나고, 다음 처리 재개 전에, 늦어도 그날 매일 정리 직후에 남은 녹음·처리 중 음성이 없다.
8. **Given** 처리 단위가 멈춰 있다, **When** 23:58 이 된다, **Then** 매일 정리는 그대로 이루어진다.
9. **Given** 다른 요청자의 작업, **When** 「다 지우기」를 요청한다, **Then** 거절되고 아무것도 지워지지 않는다.
10. **Given** 이미 지워진 작업, **When** 「다 지우기」를 다시 요청한다, **Then** 오류 없이 「이미 지움」으로 답한다.

### User Story 3 - 고친 단어장으로 같은 녹음을 다시 전사한다 (Priority: P2)

1차는 힌트·화자 구분 없이 전사한다. 호출하는 쪽의 언어 모델이 1차 전사록과 참조 단어장으로 힌트 단어장 (2)를 만든 뒤, 녹음을 다시 올리지
않고 1차 작업의 녹음을 가리키는 2차 작업을 맡긴다. 2차에는 이용자의 참조 단어장이 있어야 하므로, 참조 단어장이 없으면 호출하는 쪽은
1차에서 멈춘다. 1차 결과를 가져가는 것만으로는 아무것도 지워지지 않는다.

**Why this priority**: 전공 용어·기관명 오타를 줄이는 운영자 확정 방식이다. 다만 1회 전사만으로도 서비스는 쓸 수 있다.

**Independent Test**: 같은 녹음을 1차(힌트 없음)·2차(앞 작업 가리킴, 힌트, 화자 구분)로 맡기고, 2차가 녹음 재전송 없이 끝나며 2차를 대상으로 한 「다 지우기」 직후 녹음이 지워지는지 본다.

**Acceptance Scenarios**:

1. **Given** 완료된 1차 작업(결과를 가져갔어도), **When** 같은 요청자가 1차 작업을 가리키는 2차 작업을 맡긴다, **Then** 녹음을 다시 받지 않고 전사가 끝난다.
2. **Given** 1차 작업의 녹음이 「다 지우기」나 매일 정리로 이미 지워졌다, **When** 그것을 가리키는 2차 작업을 맡긴다, **Then** 「원본 없음」으로 거절된다.
3. **Given** 다른 요청자의 1차 작업, **When** 그것을 가리키는 작업을 맡긴다, **Then** 거절되고, 그 녹음이 있는지 없는지도 알려 주지 않는다.
4. **Given** 존재한 적 없는 작업 ID, **When** 그것을 가리키는 작업을 맡긴다, **Then** 「원본 없음」으로 거절된다.

### User Story 4 - 운영자의 손 전사와 서버 작업이 한 줄로 선다 (Priority: P2)

GPU 는 한 장이다. 서버 작업과 운영자의 명령줄 전사는 같은 줄에 서서 차례로 GPU 를 쓴다. stt 는 명령줄에서도 GPU 로만 전사한다
(운영자 결정 2026-10-22 — CPU 로 전사하지 않는다). 명령줄 사용은 그 밖에는 지금과 같다.

**Why this priority**: 겹치면 메모리 부족으로 이용자 작업이 실패한다. 운영자는 지금도 이 서버에서 손 전사를 한다.

**Independent Test**: 서버 작업이 도는 중에 명령줄 전사를 시작하고, 반대 순서로도 시작해 둘 다 끝나는지 본다.

**Acceptance Scenarios**:

1. **Given** 서버 작업이 처리 중이다, **When** 운영자가 명령줄 전사를 시작한다, **Then** 명령줄은 「서버 작업 진행 중 — 대기」를 알리고 기다렸다가 서버 작업이 끝난 뒤 전사한다.
2. **Given** 운영자의 명령줄 전사가 처리 중이다, **When** 서버 작업이 들어온다, **Then** 서버 작업은 대기 상태로 있다가 명령줄 전사가 끝난 뒤 처리된다.
3. **Given** 두 일이 동시에 시작된다, **When** 둘 다 끝난다, **Then** 메모리 부족 실패가 없다.
4. **Given** 서버 작업이 없고 GPU 를 쓸 수 있다, **When** 운영자가 기존 명령으로 전사한다, **Then** 결과와 출력이 지금과 같다(CPU 실행을 전제한 것 말고 기존 시험 전부 통과).
5. **Given** GPU 를 쓸 수 없는 컴퓨터, **When** 운영자가 명령줄로 전사·화자 구분·목소리 등록을 시작한다, **Then** CPU 로 넘어가지 않고 GPU 를 쓸 수 없다는 이유를 알리고 멈춘다.
6. **Given** 전사 엔진은 GPU 를 쓰지만 화자 구분 엔진이 GPU 를 쓸 수 없다, **When** 화자 구분 전사를 한다, **Then** CPU 로 화자 구분을 하지 않고 이유를 알리고 멈춘다.

### User Story 5 - 한도와 실패를 정직하게 알린다 (Priority: P3)

한도를 넘거나, 읽을 수 없거나, 시간이 넘거나, 품질을 지킬 수 없으면 일부 결과를 완전한 것처럼 내지 않고 실패와 그 이유를 알린다.

**Why this priority**: 이용자가 잘린 전사록을 완전한 것으로 믿고 회의록에 쓰는 일을 막는다.

**Independent Test**: 경우마다 시험 파일을 맡겨 결과 없이 실패 상태와 정해진 이유가 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 3시간을 넘는 녹음, **When** 맡긴다, **Then** 처리 전에 「길이 초과」로 거절된다.
2. **Given** 녹음이 아니거나 손상된 파일, **When** 맡긴다, **Then** 「읽을 수 없는 형식」으로 실패하고 결과는 없다.
3. **Given** 처리 시간이 상한(녹음 길이, 단 최소 5분)을 넘었다, **When** 상한에 닿는다, **Then** 처리를 멈추고 「처리 시간 초과」로 실패하며 일부 결과는 없다.
4. **Given** GPU 메모리가 모자란다, **When** 전사를 시도한다, **Then** 더 작은 모델로 대신하지 않고 「GPU 메모리 부족」으로 실패한다.
5. **Given** GPU 를 찾을 수 없다, **When** 서버 작업을 처리하려 한다, **Then** 느린 처리로 대신하지 않고 「GPU 없음」으로 실패한다.
6. **Given** 작업 내용이 형식에 맞지 않는다(빠진 칸, 알 수 없는 값, 빈 힌트 단어장), **When** 맡긴다, **Then** 「잘못된 작업」으로 거절되고 무엇이 틀렸는지 알린다.
7. **Given** 무음이거나 말소리가 없는 녹음, **When** 전사가 끝난다, **Then** 빈 전사록이 「완료」로 나오고 문단 목록이 비어 있다.
8. **Given** 실패한 작업, **When** 상태를 본다, **Then** 정해진 실패 이유 하나와 사람이 읽을 설명이 있고, 내부 오류 원문은 그대로 나오지 않는다.
9. **Given** 10초짜리 녹음, **When** 맡긴다, **Then** 모델을 올리는 시간 때문에 처리 시간 초과로 실패하지 않는다.

### Edge Cases

- 같은 작업 ID 로 두 번 맡기면: 두 번째는 「중복」으로 거절되고 첫 작업에 영향이 없다.
- 맡기는 도중 끊겨 녹음 파일이 다 오지 않았으면: 작업이 완성되지 않은 것으로 보고 처리하지 않으며, 남은 파일은 청소가 지운다(늦어도 매일 정리 때).
- 처리 단위가 멈춘 동안에도 매일 정리는 지켜진다.
- 문단 하나가 화자 경계를 넘는 짧은 맞장구일 때: 불확실 표시를 붙이고 버리지 않는다.
- 힌트 단어장의 용어 하나가 한도보다 길면: 그 용어는 빠진 용어로 보고하고 전사는 진행한다.
- 외부 접속이 막힌 상태: 전사·화자 구분 모두 정상 완료된다(외부 접속이 필요한 동작이 없다).
- 2차 작업이 아직 대기·처리 중인 1차를 가리키면: 받아들이고, 받은 순서대로 1차 뒤에 처리한다(거절할 이유가 없다 — 녹음은 이미 있다).
- 23:58 이 지나 매일 정리 대상이 된 녹음을 가리키는 2차는, 정리가 아직 돌지 않았더라도 「원본 없음」으로 거절된다. 매일 정리 대상이 된 대기 중인 작업도 시작하지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

**받기**

- **FR-001**: stt 는 호출하는 쪽이 맡긴 전사 작업을 받아 즉시 접수 확인과 대기 순서를 내야 한다(MUST).
- **FR-002**: 전사 작업은 녹음 파일 1개 또는 앞 작업 ID 1개, 언어, 힌트 단어장(선택), 화자 구분 여부, 요청자 표식을 담는다. 형식에 맞지 않으면 처리 전에 이유와 함께 거절해야 한다(MUST).
- **FR-003**: 앞 작업 ID 로 녹음을 가리키는 작업은 같은 요청자 표식일 때만 받는다. 다르거나 없는 작업이면 녹음의 존재 여부를 드러내지 않고 거절해야 한다(MUST).
- **FR-004**: 녹음 길이 3시간을 넘는 작업은 처리 전에 거절해야 한다(MUST).
- **FR-005**: 지우기 요청은 「다 지우기」 하나다 — 대상 작업의 녹음과, 그 녹음을 쓰는 모든 작업의 처리 중 음성·힌트 단어장 사본·결과를 지우고, 그 작업들이 대기·처리 중이면 멈춘다. 같은 요청자의 작업만 지운다(MUST).
- **FR-006**: stt 는 참조 단어장을 받지 않으며, 힌트 단어장을 검증·선별·재배치하지 않고 받은 순서대로 쓴다(MUST).

**하기**

- **FR-010**: 작업을 한 번에 하나씩, 받은 순서대로 처리한다(MUST).
- **FR-011**: 서버 작업과 운영자의 명령줄 전사는 같은 줄에서 GPU 를 차례로 쓴다. 명령줄은 기다릴 때 그 사실을 알린다(MUST).
- **FR-012**: 서버 작업은 정해진 최상위 전사 모델로만 처리한다. 메모리 부족이나 GPU 부재 때 다른 모델·장치로 대신하지 않고 실패로 끝낸다(MUST). 호출하는 쪽은 「GPU 없음」 실패를 받으면 이용자에게 지금은 작업할 수 없으니 나중에 다시 맡기라고 알린다.
- **FR-013**: 화자 구분을 고르면 화자를 `화자N` 으로만 표시하고, 한 전사록 안에서 같은 화자는 같은 번호다. 목소리 등록·실명 붙이기는 서버 작업에 없다(MUST).
- **FR-014**: 작업당 처리 시간이 녹음 길이(단, 최소 5분 — 모델을 올리는 시간을 감안)를 넘으면 처리를 멈추고 실패로 끝낸다(MUST).
- **FR-015**: 처리 중 외부 접속을 하지 않는다. 외부 접속이 막혀도 전사와 화자 구분이 끝나야 한다(MUST).
- **FR-016**: 대기 시간에는 별도 상한을 두지 않는다. 대기 중인 작업에도 매일 정리가 그대로 걸려, 그때까지 처리되지 못한 작업은 자료·상태와 함께 지워진다(MUST, 운영자 결정 2026-10-22).

**돌려주기**

- **FR-020**: 완료된 작업은 전사록, 문단 목록(문단마다 시작 시각·끝 시각·화자(화자 구분 시)·본문·불확실 여부), 실행 요약(모델·장치·녹음 길이·소요 시간·힌트 반영 수·전체 수·빠진 용어)을 낸다(MUST).
- **FR-021**: 상태는 대기(순서, 접수 시각과 함께)·처리 중·완료·실패·지움 가운데 하나다. 실패에는 정해진 이유 하나와 사람이 읽을 설명이 붙는다. 매일 정리가 지운 작업은 상태도 사라진다(MUST).
- **FR-022**: 일부만 된 결과를 완료로 내지 않는다(MUST).
- **FR-023**: 작업·결과·상태의 형식 정의를 함께 제공해, 호출하는 쪽이 받은 결과를 검사할 수 있게 한다(MUST).

**지우기**

- **FR-030**: 녹음·처리 중 만든 음성·힌트 단어장 사본·결과는 「다 지우기」 요청 직후, 아니면 매일 정리(23:58 KST) 직후 지운다. 매일 정리는 그 시각 전에 받은 모든 작업의 자료와 상태를 지운다(MUST).
- **FR-031**: 앞 작업의 녹음을 가리키는 작업은 그 녹음을 함께 쓴다. 공유된 녹음은 그것을 쓰는 어느 작업의 「다 지우기」나 매일 정리로 지워진다. 매일 정리가 하루 한 번 돌므로 어떤 자료도 처음 받은 때로부터 24시간을 넘지 않는다(MUST).
- **FR-032**: 처리가 강제로 끊겨 남은 녹음·처리 중 음성은 처리 재개 전과 주기적 청소로 지운다. 매일 정리는 처리 단위가 멈춰 있어도 이루어진다(MUST).
- **FR-033**: 「다 지우기」로 지운 작업의 상태(「지움」)는 매일 정리 때까지 남는다. 결과를 가져가는 것만으로는 아무것도 지우지 않는다(MUST).
- **FR-034**: 매일 정리 때 대기·처리 중인 작업은 처리를 멈추고 자료와 상태를 모두 지운다. 일부 결과를 남기지 않는다(MUST).
- **FR-035**: 처리 중 원본과 처리 중 음성은 암호화된 저장 위치에만 둔다. 처리 중 메모리 내용이 평문 스왑이나 오류 덤프(core dump)로 디스크에 내려가지 않게 한다(MUST).
- **FR-036**: 이용자별 단어장·기록·통계를 서버에 쌓지 않는다(MUST).
- **FR-037**: 서비스 기록(로그)에는 작업 ID·상태·실패 이유·시각만 남기고, 녹음 내용·전사문·힌트 단어장·요청자 표식은 남기지 않는다 — 로그는 삭제 규칙 밖에 있기 때문이다(MUST).

**명령줄**

- **FR-040**: 기존 명령줄 사용은 GPU 줄 서기와 GPU 전용(FR-041) 말고는 바뀌지 않는다(MUST).
- **FR-041**: 명령줄의 전사·화자 구분·목소리 등록은 GPU 로만 한다. CPU 로 실행하는 선택지를 두지 않고, GPU 를 쓸 수 없으면 CPU 로 넘어가지 않고 그 이유를 알리고 멈춘다(MUST, 운영자 결정 2026-10-22).

### Key Entities

- **전사 작업**: 녹음(또는 앞 작업의 녹음), 언어, 힌트 단어장, 화자 구분 여부, 요청자 표식, 받은 시각.
- **녹음**: 처음 받은 시각을 가진다. 여러 작업이 공유할 수 있고, 「다 지우기」나 매일 정리로 사라진다.
- **상태**: 작업 하나의 현재 단계, 대기 순서, 실패 이유, 지운 사실.
- **결과**: 전사록, 문단 목록, 실행 요약. 「다 지우기」나 매일 정리로 사라진다.
- **문단**: 시작·끝 시각, 화자(선택), 본문, 불확실 여부.
- **지우기 요청**: 대상 작업, 요청자 표식.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 1시간 녹음, 대기 없음 — 1차(힌트·화자 구분 없음) 10분 이내, 2차(힌트·화자 구분) 25분 이내(제안값, 시범 녹음 실측 뒤 확정).
- **SC-002**: 처리 중 stt 의 외부 접속 시도가 0건이고, 외부 접속을 막은 상태의 시험 작업이 100% 완료된다.
- **SC-003**: 지우는 길 2종(「다 지우기」·매일 정리) × 종료 방식 3종(정상·실패·강제 종료) 시험 작업 전부에서, 지운 직후 녹음·처리 중 음성·단어장 사본·결과가 서버 저장 위치에 0개다.
- **SC-004**: 매일 정리 직후 그 시각 전에 받은 작업의 상태가 0개이고, 어떤 시험 작업의 자료도 처음 받은 때로부터 24시간을 넘겨 남지 않는다.
- **SC-005**: 「다 지우기」 요청 뒤 그 녹음을 쓰는 작업들의 파일이 1분 안에 0개가 되고, 상태에 지운 사실이 남는다.
- **SC-006**: 2차 작업 시험 전부가 녹음 재전송 없이 끝난다. 다른 요청자·지워진 녹음·없는 작업을 가리킨 시험은 100% 거절된다.
- **SC-007**: 화자 구분 결과 전부에서 `화자N` 밖의 이름이 0건이다. 시범 녹음에서 한 사람이 한 전사록 안에서 번호가 바뀐 경우가 사람 확인으로 0건이다.
- **SC-008**: 힌트 단어장을 쓴 결과 100%에 반영 수·전체 수·빠진 용어가 있다.
- **SC-009**: 길이 초과·읽을 수 없는 형식·처리 시간 초과·GPU 메모리 부족·GPU 없음·잘못된 작업 시험 파일 전부에서 완료 결과가 0건이고 정해진 실패 이유가 나온다.
- **SC-010**: 명령줄 전사와 서버 작업을 동시에 시작한 시험 전부에서 둘 다 완료되고 메모리 부족 실패가 0건이다.
- **SC-011**: 모든 시험 작업에서 접수 확인과 대기 순서가 맡긴 직후 나온다.
- **SC-012**: 호출하는 쪽이 모든 시험 결과를 stt 의 형식 정의로 검사해 100% 통과한다.
- **SC-013**: 기존 명령줄 시험이 100% 통과한다. CPU 실행을 전제한 시험만 GPU 전용 동작에 맞게 바꾼다(운영자 결정 2026-10-22).
- **SC-014**: GPU 를 쓸 수 없는 환경의 명령줄 전사·화자 구분·목소리 등록 시험 전부가 CPU 로 넘어가지 않고 이유와 함께 멈춘다.

## Assumptions

- 호출하는 쪽은 bhu-llm 하나이고, 이용 대상은 연구 보고서 모드의 `report-authors`(약 14명)다. 동시 처리는 하나로 충분하다.
- 업로드 상한(100MB)과 확인 창·안내 문구·완료 알림(메일 등)은 bhu-llm 이 맡는다. 매일 정리 안내(「자정 무렵 유지관리로 작업 결과물과 자료가 사라질 수 있으니 자정 이후에 맡기라」)와 「GPU 없음」 안내도 bhu-llm 이 이용자에게 보인다.
- 요청자 표식은 bhu-llm 이 확인한 값을 그대로 믿는다. stt 는 그 값을 같은 요청자 확인에만 쓴다.
- 언어는 호출하는 쪽이 작업마다 정한다(보통 `ko`). stt 가 정하는 기본값은 없다. 영상과 장면 사진은 이번 범위 밖이다(운영자 결정 2026-10-21).
- 매일 정리는 대기 중인 작업에도 걸린다(US2-5). 그 밖의 대기 상한은 두지 않는다(FR-016).
- 힌트 단어장 (2)를 만들고 참조 단어장 (1)로 검증하는 일, 화자별 통계, 회의록·강의록 정리는 호출하는 쪽의 일이다(`idea.md` 「호출하는 쪽이 맡는 일」).
- 화자 판정 불확실 기준은 지금의 명령줄 기본값(짧은 문단)을 그대로 쓴다.
- SC-001 의 시간 근거: 화자 구분 없이 48분 녹음 약 4분(이 서버), 22분 녹음 화자 구분 포함 약 6분 30초(같은 종류 GPU) — `tech-notes.md` §7.
