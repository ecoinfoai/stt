## Background

- 운영자는 bhu-llm 연구 보고서 모드에서 교수·직원이 녹음을 올려 전사록과 그 정리(회의록·강의록)를 받게 하기로 했다(2026-10-15).
  전사는 stt 가 교내 서버 GPU 에서 하고, 정리는 bhu-llm 이 한다. 영상은 나중에 하고 음성 파일부터 한다(2026-10-21).
- stt 는 지금 운영자의 명령줄 도구다. 맡은 일을 받아 차례로 처리하는 방식, 결과 약속, 서버 배포가 없어서 bhu-llm 이 부를 수 없다.
  bhu-llm 은 이것이 끝나 배포되기 전에는 stt 를 부르지 않는다(핸드오프 S1~S11).
- 48분 녹음이 이 서버에서 화자 구분 없이 약 4분에, 22분 녹음이 같은 종류의 GPU 에서 화자 구분을 포함해 약 6분 30초에 전사됐다.
- 전사록에는 전공 용어·기관명 오타가 제법 많다. 힌트 단어장은 엔진 한도 때문에 짧은 용어 약 40개까지만 쓰인다.

## Problem

- **교수·직원**은 녹음을 전사록으로 바꾸려면 운영자에게 부탁하거나 외부 서비스에 올려야 한다. 외부에 올리면 다른 참석자의 목소리와
  발언이 학교 밖으로 나간다.
- 녹음 자체가 개인정보다. 서버에 오래 남거나, 처리 중 실패한 작업의 파일이 남으면 그만큼 위험하다.
- 전공 용어와 기관명이 틀리게 적힌다. 교수마다·주제마다 단어장이 다르고, 긴 단어장은 앞쪽 일부만 쓰인다.
- GPU 는 한 장이고 운영자의 손 전사도 같은 GPU 를 쓴다. 두 일이 겹치면 한쪽이 메모리 부족으로 실패할 수 있다.

## Desired Outcome

bhu-llm 이 녹음을 맡기면 stt 가 차례로 전사해 정해진 형식으로 돌려주고, 원본은 정한 때에 지운다. 같은 녹음을 고친 단어장으로 한 번 더
전사할 수 있다. stt 의 역할은 넷뿐이다(운영자 확정 2026-10-22).

| 동사 | 내용 |
|---|---|
| 받는다 | 녹음 1개(또는 앞 작업의 녹음), 언어, 힌트 단어장(선택), 화자 구분 여부(선택), 원본 삭제 시기, 요청자 표식 |
| 한다 | 전사, 화자 구분, 힌트 단어장 반영 수 세기 |
| 돌려준다 | 전사록, 문단 목록(시작·끝·화자·본문·불확실 표시), 실행 요약(모델·장치·녹음 길이·소요 시간·반영 N개/전체 M개·빠진 용어), 실패 이유 |
| 지운다 | 녹음·처리 중 만든 음성·단어장 사본·결과 — 정한 때에, 그리고 「지금 지우기」 요청을 받으면 바로 |

stt 가 하지 않는 일: 참조 단어장을 받거나 힌트 단어장을 검증·선별·배치하기, 화자별 통계, 오인식 보고, 교정 규칙, 회의록 작성·검색,
언어 모델 호출, 목소리 등록(실명 붙이기), 영상 처리.

### 단어장 두 개와 두 번의 전사 (운영자 확인 2026-10-22)

1. 교수가 시스템 밖에서 자기 교재의 핵심 용어로 **참조 단어장 (1)** 을 만든다. 길이 제한이 없고 정답 표기의 기준이다. stt 에는 오지 않는다.
2. stt 가 힌트 없이, 화자 구분 없이 **1차 전사**를 한다.
3. 호출하는 쪽의 언어 모델이 1차 전사 전체와 (1)을 읽고, 맥락으로 오인식된 (1)의 용어를 골라 **전사 단어장 (2)** 를 만든다.
   언어 모델은 전사록을 고치지 않는다.
4. stt 가 1차의 녹음을 가리키는 작업으로 (2)를 힌트로, 화자 구분을 켜고 **2차 전사**를 한다.

### 호출하는 쪽(bhu-llm)이 맡는 일 — bhu-llm 과 함께 정리할 것

- 위 3단계: (2)의 모든 용어가 (1)에 그대로 있는지 확인하고, 중요한 순서로 짧게(약 30개 이내) 맞춘다. 결과에 빠진 용어가 있으면 다시 맡긴다.
- 두 번 맡기는 흐름을 이용자에게 보이는 방식과 완료 알림 방식.
- 회의록에 쓸 화자별 통계(발언 시간 등)는 문단 목록으로 계산한다.
- 결과를 복사한 직후 stt 에 「지금 지우기」를 보낸다.
- bhu-llm `tech-notes.md` §4.2(이용자 단어장을 그대로 힌트로 쓰는 안)를 위 흐름으로 고친다. 확인 창의 「반영 N개 / 전체 M개」는 (2)의 값이다.

### User Scenarios

- **교수**는 수업 녹음과 교재에서 뽑은 참조 단어장을 넣어 전공 용어가 맞게 적힌 강의 전사록을 받고 싶다. 왜냐하면 일반 전사는 전문 용어를 엉뚱한 낱말로 바꾸기 때문이다.
- **직원**은 회의 녹음을 `화자1`·`화자2`로 구분된 전사록으로 받고 싶다. 왜냐하면 회의록에는 누가 무엇을 말했는지가 필요하지만 이름을 서버에 맡기고 싶지는 않기 때문이다.
- **이용자**는 맡긴 작업의 대기 순서와, 실패했다면 그 이유를 알고 싶다. 왜냐하면 결과가 오는지 모르는 채로 기다릴 수 없기 때문이다.
- **이용자**는 원본 녹음이 언제 지워지는지 알고, 필요하면 바로 지우고 싶다. 왜냐하면 녹음에는 다른 참석자의 목소리가 담겨 있기 때문이다.
- **운영자**는 지금처럼 명령줄로 손 전사를 하면서도 서버 작업과 부딪히지 않기를 원한다. 왜냐하면 GPU 가 한 장이고, 겹치면 이용자 작업이 실패하기 때문이다.

## Constraints

- 역할은 최소로: 위의 네 동사 밖의 일은 stt 에 넣지 않는다. 호출하는 쪽이 stt 의 결과로 할 수 있는 일은 그쪽이 한다(운영자 2026-10-22).
- 원본은 교내 서버에서만 다룬다. 처리 중에 stt 는 외부에 접속하지 않는다. 처리 중 원본은 암호화된 저장 위치에만 둔다.
- 음원은 개인정보다. 녹음·처리 중 만든 음성·단어장 사본은 작업이 정한 때(「끝나면 바로」 또는 「자정」)에 지우고, 어떤 경우에도
  **처음 받은 때로부터 24시간**을 넘기지 않는다. 실패·멈춤·강제 종료된 작업도 같다. 2차 작업이 1차의 녹음을 가리켜도 24시간은 처음 받은 때부터 센다.
- 결과도 개인정보다. 호출하는 쪽이 가져간 뒤 지우기 요청을 받으면 지우고, 가져가지 않은 결과는 그 작업을 받은 때로부터 24시간에 지운다.
- 앞 작업의 녹음은 **같은 요청자**의 작업만 가리킬 수 있다. 다르면 거절한다.
- 화자는 `화자N` 으로만 적는다. 한 전사록 안에서 같은 사람은 끝까지 같은 번호다. 목소리 등록과 실명 붙이기는 서버 경로에 없다(운영자 결정 2026-10-15).
- 단어장: stt 가 받는 것은 힌트 단어장 (2)뿐이고 작업마다 받아 쓰고 지운다. 이용자별로 아무것도 쌓지 않는다(운영자 결정 #5).
- 말없이 자르지 않는다: 일부만 된 결과를 완전한 것처럼 내지 않고, 반영되지 않은 힌트가 있으면 그 수와 용어를 결과에 적는다.
- 한 번에 한 작업. 운영자의 손 전사도 같은 줄에 선다(운영자 결정 2026-10-22).
- 한도: 녹음 길이 3시간, 작업당 처리 시간은 녹음 길이만큼(운영자 결정 2026-10-22). 넘으면 실패로 끝내고 이유를 남긴다.
- 서버 전사는 정해진 최상위 모델로만 한다. 품질을 낮춰 대신 내지 않고 실패로 끝낸다.
- 독립성: stt 는 bhu-llm 없이도 명령줄 도구로 지금처럼 돈다. 두 프로젝트는 정해진 약속으로만 만난다.

## Success Criteria

- SC-1: 처리 시간 — 1시간 녹음, 대기 없음: 1차 10분 이내, 2차(힌트·화자 구분) 25분 이내. 시범 녹음으로 잰다(제안값, 실측 뒤 확정).
- SC-2: 외부 전송 0 — 처리 중 stt 의 외부 접속 시도가 0건이다. 외부 접속이 막힌 상태에서도 전사·화자 구분이 끝난다.
- SC-3: 원본 삭제 — 「끝나면 바로」는 완료 직후, 「자정」은 자정 직후, 어떤 경우에도 처음 받은 때로부터 24시간 안에 녹음·처리 중 음성·단어장 사본이
  서버의 모든 저장 위치에 없다. 정상·실패·강제 종료 세 경우의 시험 작업으로 확인한다.
- SC-4: 결과 삭제 — 지우기 요청 직후, 또는 가져가지 않았으면 받은 때로부터 24시간 안에 결과가 없다.
- SC-5: 「지금 지우기」 — 요청 즉시 그 작업의 모든 파일이 지워지고, 지운 사실이 상태에 남는다.
- SC-6: 두 번의 전사 — 2차 작업이 녹음을 다시 받지 않고 1차의 녹음으로 전사된다. 녹음이 이미 지워졌거나 요청자가 다르면 이유와 함께 거절된다.
- SC-7: 화자 표시 — 화자 구분을 켠 결과에 `화자N` 밖의 이름이 0건이고, 시범 녹음에서 같은 사람이 한 전사록 안에서 다른 번호로 바뀐 경우가 사람 확인으로 0건이다.
- SC-8: 단어장 보고 — 힌트 단어장을 쓴 모든 결과에 반영 N개 / 전체 M개와 빠진 용어가 있다(100%).
- SC-9: 정직한 실패 — 한도 초과, 읽을 수 없는 형식, 처리 시간 초과, GPU 메모리 부족의 시험 파일에서 결과 없이 실패 상태와 이유만 나온다.
- SC-10: GPU 줄 — 손 전사와 서버 작업을 동시에 시작해도 한쪽이 기다렸다가 둘 다 끝나고, 메모리 부족 실패가 0건이다.
- SC-11: 대기 표시 — 접수 즉시 접수 확인과 대기 순서가 나오고, 완료·실패까지 상태를 언제든 확인할 수 있다.
- SC-12: 결과 검사 — stt 가 결과 형식의 정의를 함께 내놓아, 받는 쪽이 모든 시험 결과를 그 정의로 검사해 통과한다.
- SC-13: 명령줄 유지 — 기존 명령줄 사용이 그대로 동작한다(기존 시험 전부 통과).
