## 1. 요약

- 운영자는 bhu-llm 연구 보고서 모드에서 교수·직원이 녹음을 올려 전사록과 그 정리(회의록·강의록)를 받게 하려 한다. 전사는 stt 가 교내
  서버 GPU 에서 하고, bhu-llm 은 맡기기·상태 보기·결과 받기만 한다.
- 지금 stt 는 운영자의 명령줄 도구다. 서버에서 맡은 일을 받아 처리하는 방식, 결과 약속, 서버 배포가 없다.
- **가장 먼저 볼 것은 용어 사전 한도(S9)다.** 운영자의 2026-10-15 전사 작업 기록: 「기존 terms.txt: 137개, 818토큰이라 앞쪽 약 3분의 1만
  실제로 반영되고 있습니다. 이번 작업 범위 밖이라 손대지 않았습니다.」 원인은 아래 §3 S9 에 있다. bhu-llm 과 상관없이 지금 명령줄
  사용에도 해당한다.

## 2. 운영자 결정 (2026-10-15) — stt 에 걸리는 것

## 3. stt 할 일

## 4. 삭제 시기 — bhu-llm 세션 제안, 운영자 확인(2026-10-15)

> **2026-10-22 운영자 결정으로 바뀌었다.** 아래의 「바로 삭제 / 자정까지 보관」 고르기는 없다. 지우기는 「다 지우기」 요청과
> 매일 23:58 정리뿐이다 — §8 참고. 아래는 당시 제안 기록으로 남긴다.

- 접수 확인 창에서 묻는다: [전사가 끝나면 바로 삭제] / [오늘 자정까지 보관 — 그 사이 같은 녹음으로 다시 전사할 수 있음].
- 「바로 삭제」면 완료 즉시 지운다. 「보관」이면 자정(00:00, KST)에 지우고, 결과 안내에 「원본 녹음은 오늘 24:00 에 삭제됩니다」를 적는다.
  보관 중에도 「지금 지워줘」 하면 바로 지운다(S11).
- 어떤 경우에도 받은 뒤 24시간을 넘기지 않는다(S4).
- 「대화가 끝나면 삭제」는 쓰지 않는다. 대화가 끝났다는 신호가 없다(이용자는 창을 닫을 뿐이다).
- 단어장 사본과 내려받기용 파일(전사록·단어장)도 같은 자정에 지운다. 전사록 본문은 대화 안에 남고 대화 보존 규칙을 따른다(bhu-llm 쪽).

## 8. 호출하는 쪽에 넘길 계약 요점 (stt, 2026-10-22)

정본은 `specs/001-server-transcription/contracts/`(JSON Schema 셋과 README)다. 아래는 bhu-llm 이 꼭 알아야 할 것만 추린 것이다.

**통로와 파일**
- `requests/inbox/<request_id>.json`(+ 첨부 `<request_id>.audio.<ext>`)을 쓰고, `requests/outbox/<request_id>.json`(응답)과
  `outbox/<request_id>/`(결과: `transcript.txt`, `result.json`)를 읽는다. 쓰기·읽기 권한은 `stt-requests` 그룹(호스트가 OWUI 계정을 넣는다).
- 첨부를 먼저 다 쓰고, 요청은 `.tmp` 로 쓴 뒤 이름을 바꾼다. 두 파일 모두 그룹이 읽을 수 있는 일반 파일(0640 또는 0660). 요청 JSON 은 1 MiB 이하.
- `request_id` 는 요청마다 새 소문자 UUID. `schema_version` 은 1 이다(처음 내놓는 판).

**응답의 꼴 셋**: 전사 요청에는 작업 상태(`kind: transcribe`), 지우기 요청에는 지우기 답(`kind: delete`), 쓸 수 없는 요청에는 거절
(`kind: invalid`, 이유 `invalid_request`). 스키마로 검사하고, 이용자 문구는 `failure.reason` 으로 고른다(`detail` 은 운영자 기록용 영어).
실패 이유는 11개다: `invalid_request` `audio_too_long` `unreadable_audio` `source_unavailable` `audio_deleted` `processing_timeout`
`gpu_out_of_memory` `gpu_unavailable` `models_unavailable` `interrupted` `engine_error`.

**지우기 — 2026-10-22 운영자 결정(§4 를 대체한다)**
- 지우는 길은 둘뿐이다: ① 이용자가 일을 마치면(1차에서 멈추든 2차까지 하든) bhu-llm 이 보내는 「다 지우기」 — 그 녹음을 쓰는 1차·2차의 녹음과
  회의록 재료(결과·단어장 사본)를 즉시 모두 지운다. ② 매일 23:58(KST) 정리 — 그날 받은 모든 것(대기·처리 중인 작업 포함)을 지운다.
- 응답의 `expires_at` 과 `audio.delete_at` 은 받은 날의 23:58(KST, UTC 로 적힘)이다. 결과를 가져가는 것만으로는 아무것도 지워지지 않는다.
- 2차 전사는 같은 날 안에 1차 녹음을 가리켜(`audio.from_request`) 맡긴다. 23:58 뒤에는 그 녹음이 없어 `source_unavailable` 이다.
- 응답 파일이 사라졌으면 만료된 것이다. 정리 때 끝나지 못한 작업은 실패가 보이지 않고 응답째 사라질 수 있다.
- 정리로 이미 지워진 작업에 보낸 「다 지우기」는 `refused` 로 답한다 — 전날 작업이면 이미 지워진 것으로 본다.

**bhu-llm 이 이용자에게 보일 것**
- 매일 정리 안내: 「자정에 유지관리로 작업 결과물과 자료가 사라질 수 있으니 자정(00:00) 이후에 맡기세요.」 23:58~24:00 에 맡긴 작업은
  처리되지 못하고 지워진다.
- `gpu_unavailable`: 「현재 GPU 를 쓸 수 없어 작업할 수 없습니다. 나중에 다시 요청하세요.」 stt 는 CPU 로 전사하지 않는다(명령줄 포함).
- 대기 중이면 `queue_position`(1 = 다음 차례)을 보일 수 있다. 완료 알림(메일 등)은 bhu-llm 이 한다 — stt 는 알리지 않는다.
- 힌트 단어장을 썼으면 `summary.hints` 의 「반영 N개 / 전체 M개」와 빠진 용어.

**운영 신호**
- 맡긴 뒤 5분 안에 응답 파일이 생기지 않으면 실패로 보고 운영자에게 알린다(받기 단위가 멈춘 것).
- 처리 시간 상한은 max(녹음 길이, 5분), 녹음 길이 상한은 3시간. 대기 시간에는 따로 상한이 없다(정리가 끝이다).

**단어장 흐름(2026-10-22)**: 1차는 힌트 없이 맡긴다 → bhu-llm 의 언어 모델이 1차 전사록과 참조 단어장 (1)로 힌트 단어장 (2)를 고른다 →
2차에 `hints` 로 (2)를 싣는다. 참조 단어장이 없으면 1차에서 멈춘다. stt 는 (1)을 받지 않고 (2)를 고치지 않는다.
